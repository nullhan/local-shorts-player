# 网盘 / 远程媒体播放 · 技术分析

结论先行：**可行，但不是「填个网盘地址就能播」那么简单。**
核心矛盾是浏览器安全模型：你无法在一个普通网页里随意读取第三方网盘的文件。
下面按可行性从高到低给出路径，并说明每条路的代价。

---

## 0. 先厘清一个常见误解

很多人以为「浏览器的 `<audio>` / `<video>` 可以随便播跨域 URL，只有 `fetch` / `XHR` 受 CORS 限制」。
**这个说法不对。** 准确情况是：

| 场景 | 是否需要 CORS |
| --- | --- |
| `<audio src="跨域">` 直接播放 | **不需要**（媒体元素是允许跨源加载的特例） |
| `<audio crossorigin="anonymous">` | 需要，服务端必须回 `Access-Control-Allow-Origin` |
| 用 `fetch` / `XHR` 取媒体再喂给元素 | 需要（这是最常见的踩坑方式） |
| `createMediaElementSource()`（接 Web Audio 做可视化 / EQ） | 需要，否则音频被"污染"后**静音输出** |
| `crypto.subtle.digest` / Service Worker / Wake Lock / Media Session | 需要**安全上下文**（https 或 localhost） |

**这意味着：只要拿到一个能直接 GET 到文件内容的直链，`<audio>` 就能播，不需要对方配 CORS。**

但这里有个陷阱 —— 网盘给的"直链"往往不是真的文件直链：
- 它可能返回 JSON（元信息）而不是字节流
- 它可能是 302 跳转到临时签名 URL，且该 URL 对 Referer 敏感
- 它可能对非浏览器 UA 限速 / 拒绝

所以真正的难点不在 CORS，而在**「怎么稳定地拿到字节流 URL」**。

## 1. 可行性排序

### 路径 A：本地小助手代理（★★★★★ 推荐）

本项目**已经有一个可用的本地小助手**（`tools/reveal-helper.mjs`），而且我实测验证过这条路是通的：

```
公网 HTTPS 页面 (https://nullhan.github.io)
      ↓  fetch  实测结果：200 OK（GET 与 POST 预检均通过）
本机 http://127.0.0.1:17897
      ↓
本地磁盘 / 网盘 SDK
```

**这是本项目最大的既有优势** —— 一旦有一个本机进程，前面所有浏览器限制全部消失：

- CORS：由小助手自己发请求，它是 Node，不受同源策略约束
- 鉴权：OAuth token / Cookie / AK-SK 都可以安全地放在本机，**不用暴露给网页**
- 协议：可以对接 WebDAV / SMB / 各家网盘私有 API / rclone
- 转码：必要时能在本机转码后再喂给浏览器

```js
// helper 侧新增一个 /stream 路由的示意
// 关键点：返回 206 + 正确 Content-Range，浏览器才能拖进度条
if (req.headers.range) {
  const { start, end } = parseRange(req.headers.range, size)
  res.writeHead(206, {
    'Content-Range': `bytes ${start}-${end}/${size}`,
    'Accept-Ranges': 'bytes',
    'Content-Length': end - start + 1,
    'Content-Type': mimeOf(path)
  })
  createReadStream(absPath, { start, end }).pipe(res)
}
```

代价与注意点：
- 用户要装 / 跑一个 Node 程序（**这是最大的落地门槛**，非技术用户会卡住）
- 网页要能从公网访问 127.0.0.1 —— 我实测当前 Chrome 版本可以，
  但这依赖 **Private Network Access / Local Network Access 的现状**，
  而 Chrome 正在逐步收紧（142 起对公网→本地请求加权限门控，
  早期 PNA 提案要求 `Access-Control-Allow-Private-Network: true` 预检头，
  本项目 helper 已带这个头）。**这条路的长期稳定性依赖浏览器厂商策略，需要持续关注。**
- 已有 `--allow-origin` 白名单机制，必须保持（否则任意网站都能调用用户本机程序）

> 现状：helper 已经处理了 `Access-Control-Allow-Private-Network`、
> origin 白名单、超时控制。要做网盘，只需在里面加「认证 + 列表 + 流式读取」三块。

### 路径 B：WebDAV 直连（★★★☆☆ 可用但门槛高）

WebDAV 是标准协议，理论上网页可以直接 `PROPFIND` 列目录、`GET` 取文件。

现实问题（社区反馈高度一致）：

1. **绝大多数 NAS / 网盘 WebDAV 默认不发 CORS 头**。
   浏览器直接 `fetch` 会被拦，而且这不是加个参数能绕的 —— 要么服务端配，要么走代理。
2. **即使不发 CORS 头，`<audio src>` 仍能播**（见第 0 节）。
   但你就**拿不到目录列表**（列目录必须走 `fetch`），只能靠用户手动填单个文件直链。
3. 认证：HTTP Basic 认证放在 URL 里（`https://user:pass@host/...`）
   现代浏览器已基本废弃；要自己发 `Authorization` 头又绕回了 CORS 预检。
4. 群晖 / 威联通默认 WebDAV 需要 SSH 改 Nginx 才能加 CORS，普通用户做不到。

**结论：WebDAV 直连适合"用户自己能配好 CORS 的技术用户"，不适合做默认方案。**
如果要支持，最好的形态是：**WebDAV + 本地小助手代理**（把 WebDAV 读取放在 helper 里，绕开 CORS）。

### 路径 C：自家 / 企业网盘后端（★★★★☆ 取决于你能否改服务端）

如果这个播放器要对接**你们自己的**存储服务，那这反而是最优解：

- 服务端加 `Access-Control-Allow-Origin` + `Accept-Ranges: bytes` 即可，成本极低
- 直链可控、鉴权走标准 Bearer token、支持 Range 就能拖进度条
- 不需要用户装任何东西

这是唯一"完全干净"的方案，**前提是你能改服务端**。

### 路径 D：商业网盘开放平台（★★☆☆☆ 有法律与稳定性风险）

阿里云盘 / 百度网盘等有开放平台 API，但：

- 多数需要**企业开发者资质**，个人拿不到 key
- 返回的是**有时效的签名直链**（通常几小时），需要频繁刷新
- 大厂明确限制第三方播放器使用（百度网盘尤其严格，非会员限速）
- 第三方聚合工具（AList 等）大多是**逆向接口**，随时可能失效，且存在 ToS 风险
- 免费额度 / 限速策略变化频繁，做进去可能明天就坏

**建议：不作为主力方案**，最多做成"可插拔适配器"让用户自己填。

## 2. 无论走哪条路，都必须处理的技术点

### 2.1 HTTP Range（拖进度条的前提）

没有 `206 Partial Content`，进度条就是坏的 —— 尤其是 1GB 以上的文件。
服务端必须支持 `Range` 请求并回 `Accept-Ranges: bytes`。

本项目**已经写好了 Range 直通逻辑**（见 `public/media-sw.js`）：
带 `Range` 的请求直接放行给网络，只缓存完整的 200 响应。这是有意的 ——
把 206 分片缓存下来会让后续播放读到残缺数据。

### 2.2 鉴权不能放在前端

网盘的 access token 如果直接写在前端代码 / localStorage，等于公开。
**正确做法**：token 只存在于本地小助手（或你自己的后端），
网页只跟"自己的"服务对话。这也是路径 A 相对路径 D 的关键优势。

### 2.3 断点与缓存

移动端网络会断。Service Worker 可以做：
- 已完成分块的缓存，重连后用缓存续上
- 但**不要缓存 206 分片**（半截数据比没数据更糟）

### 2.4 移动端后台播放

这点**已经实现**（见下节），对网盘场景尤其重要 —— 手机锁屏后如果播放断了，
用户会认为"这功能不能用"。

## 3. 本次已实现的（不依赖网盘）

为了给后续接网盘打好地基，本轮先做了这些：

| 能力 | 说明 |
| --- | --- |
| **音频支持** | `MediaKind` 区分音视频；音频用 `<audio>` 宿主（移动端系统按音频会话处理，锁屏行为更正确） |
| **音乐界面** | 封面 + 标题 + 专辑信息，封面由文件名确定性生成（零依赖、无 IO） |
| **Media Session** | 锁屏 / 通知栏 / 耳机线控 / 车机可控制，含 `seekto`。已实测 metadata 正确发布 |
| **Wake Lock** | 音乐模式播放时防息屏；视频模式不启用（用户在看着） |
| **Service Worker** | 媒体请求 Range 直通 + 完整响应缓存兜底，提升后台播放稳定性 |
| **触摸手势** | 上下滑切换、双击快进/快退，阈值与轴判定都做了防误触 |
| **移动端布局** | 安全区适配（刘海/home 条）、44px 点击区、`100dvh`、轨道改横排、面板全屏化 |
| **PWA 元信息** | 可"添加到主屏幕"当 App 用；`viewport-fit=cover` |

之所以先做这些：**网盘只是"内容来源"，而上面这些是"播放能力"。**
播放能力做好了，之后无论接本地盘、WebDAV 还是网盘，都能直接受益。

## 4. 建议的落地顺序

```
第 1 步（已完成）  音频能力 + 移动端 + 后台播放 + SW
第 2 步            把 helper 扩展成「媒体代理」：
                   加 /list /stream /auth 三个路由，先接本地目录验证 Range 与断点
第 3 步            在 helper 里接 WebDAV（rclone 或 webdav 客户端），
                   网页侧零改动 —— 因为流已经是标准 http://127.0.0.1/stream
第 4 步（可选）    网盘适配器：把各家 SDK 收进 helper，做成可插拔配置
```

**关键设计建议：让第 2 步的 `/stream` 成为唯一入口。**
这样浏览器侧永远只面对"一个支持 Range 的普通 HTTP 地址"，
网盘 / WebDAV / 本地盘的差异全部被 helper 吸收掉。
以后换协议、加网盘，前端一行都不用改 —— 这是这个方案最重要的架构收益。

## 5. 风险与限制（需要你决策的点）

1. **本地小助手是最大门槛**：非技术用户不会跑 Node 程序。
   如果目标用户包含他们，需要打包成 exe / dmg 双击即用（可用 `pkg` / `node-single-executable`）。
2. **公网 → 127.0.0.1 的长期可用性**：当前实测可用，但 Chrome 在收紧本地网络访问。
   如果哪天被默认阻断，需要改成本地起一个 https 服务 + 自签证书，或改用 PWA 同源部署。
3. **商业网盘的合规风险**：第三方播放器接入大厂网盘，接口随时可能变或被封。
   建议只做"用户自己填地址"的适配器，不做内置 key。
4. **iOS Safari 的限制**：`showDirectoryPicker` 没有、后台音频会被系统挂起
   （Media Session 能保住锁屏控制，但长音频仍可能被回收）。
   纯 Web 在 iOS 上做不到 100% 可靠的后台播放，这是平台限制。
